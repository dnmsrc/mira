# 架构 v4：决策层独立 + 陌生人兜底

> 取代 PLAN_v3 里「S1 只产出 ask、emotion/action 由拍位决定」的折中方案。
> v3 的问题是：**选择仍然发生在 4B 的生成过程里**（它输出首行指令），
> 只不过把选项收窄了。选项再窄，选择的质量仍然取决于那个被要求同时干三件事的模型。

## 一句话

**理解归 4B，选择归选择题模型，兜底归场景门。**

4B 不再输出任何指令，只做两件事：读懂对方这句话（产出结构化理解），把已经决定好的内容说成自然台词。
「她现在该是什么情绪 / 该演什么动作 / 该不该推进剧情」变成一道**有固定候选集的单选题**，
交给一个 cross-encoder（bge-reranker）打分决定；所有候选都不过门 → 角色进入**陌生人状态**。

## 为什么必须这么拆（不是审美，是实测）

| 做法 | 实测 | 结论 |
|---|---|---|
| 4B 一次输出「台词 + 指令」 | 答案错时没有任何信号，只能靠事后正则纠 | 选择不可观测、不可阈值化 |
| 正则判意图（v2/v3 现状） | 一句里命中多个模式时靠规则顺序，写死 18 条规则仍然漏 | 规则覆盖不了自然语言的长尾 |
| mDeBERTa-xnli 做零样本分类 | top1 3/15，1382 ms/轮 | 中文语义匹配不是它的强项，淘汰 |
| **bge-reranker 做 cross-encoder 选择** | **top1 16/16（在场台词），177 ms/轮（CPU）** | **采用** |

标定数据（`tools/qa/selector_calibrate.py`，21 条人工标注，可复跑）：

```
场景门 in-scene 最低 = +1.83      ← 「照片里是谁？」「我能坐这儿吗？」
场景门 off-topic 最高 = -1.73     ← 「今天中午吃什么」「你玩原神吗」
→ 两组之间 3.56 的空隙，阈值取中点 0.0，两边各留 1.7+ 余量
槽位 top1：16 条在场台词全对；5 条跑题全部被门拦下
```

### 为什么兜底不能只靠 argmax（这条最重要）

argmax **永远有答案**。实测「今天中午吃什么」在 10 个槽位里被选成 `coffee`（-0.24）——
不是模型坏了，是"在这 10 个里选一个"这个动作本身就不允许它回答"都不像"。

所以兜底必须是**独立的一道门**：先问「这句话是不是还在这个场景里」，
用同一批「在场台词原型」当 passage 取最大分。门外的话直接进陌生人状态。
这也是为什么这个设计能对着题面讲：**拒绝是一种显式能力，不是概率为 0 的意外。**

## 三层

```
用户一句话
   │
   ├─① 场景门（cross-encoder，16 条在场原型取 max）
   │     gate < 0.0 ──────────────────────────► 陌生人状态
   │
   ├─② 选择题（cross-encoder，10 个槽位取 argmax + margin）
   │     margin < 0.3 ────────────────────────► 陌生人状态（没听懂，不硬猜）
   │
   └─③ 理解层（4B）：拿槽位对应的 content + anchors，产出自然台词
         │
         └─④ 首句闸门（已有）：答没答到那件事上 / 有没有复读 / 有没有旁白
```

① 和 ② 是同一个模型的两次打分，可以合并成一次 batch（25 个 pair，177 ms）。
③ 的输入是**已经决定好的东西**，它没有任何选择权——这是小模型能用的前提。

## 陌生人状态（题面要求的最终兜底）

语义（用户指定）：**角色不说话，字幕上给一行旁白，说明她现在不想接这句话；旁白不朗读。**

- 不调 LLM、不合成 TTS、**不推进节拍**（否则"她不理你"却把剧情推走了）
- 不换表情、不换场景（"不理你"却切镜头 = 出戏）
- 旁白文本放卡包 `narration.stranger`（数据驱动，可轮换）
- 前端：字幕区显示旁白（样式上与台词区分），停 1.2–1.8s 后淡出，恢复可输入

**顺带解决题面一个硬项**：§14 演示录屏要求「必须包含至少一种失败或降级状态」。
以前只能现场制造一个 TTS 失败来演；现在陌生人状态本身就是一个**设计好的、可复现的降级演出**。

## 成本与降级

| 项 | 值 |
|---|---|
| 模型 | bge-reranker-base（278M 参数），本地目录 `D:\ai\mira-models\bge-reranker-base` |
| 单轮耗时 | 177 ms（CPU，25 pair 一次 forward；首次加载 ~1.5 s） |
| 依赖 | torch(cpu) + transformers，**可选**：装不上时 `selector.py` 自动降级为关键词门，返回 `backend="keyword"`，服务照常起 |
| 降级诚实性 | 降级后的决策质量必须显式下降并标明 backend，不静默用坏结果 |

## 与题面评分点的对应

| 题面要求 | 本层的回答 |
|---|---|
| 结构化角色/场景指令（情绪/动作/镜头/特效/事件/分支） | 候选集就是卡包 directives；选择层只在卡包给定的枚举里选，越界值**进不了候选集** |
| 视觉事件不能只按固定计时器 | 事件同样走选择题：候选是 event 枚举，由这句话的语义决定，不设计时器 |
| 无需私人密钥可看核心流程 | 选择题模型是**本地权重**，不依赖任何 API key；缺模型时走 keyword 降级仍可演示 |
| 失败/降级状态 | 陌生人状态即降级演出，可复现、可讲 |
| 小模型（4B）如何撑住体验 | 因为它不再需要做选择——选择被搬到 177ms 的专用模型上 |

## 写进讲解的三个不变量（更新）

1. **卡 = 数据契约**：候选集来自卡包，模型只能在枚举里选；越界值在候选集层面就不存在。
2. **TurnIR = 一轮唯一产物**：新增 `stranger` 与 `narration` 两个字段，陌生人状态也是一份合法的 TurnIR。
3. **拒绝是显式状态**：`accepted: false` 是一个有原因（`off_scene` / `low_margin`）的一等公民，不是降级补丁。

## 决策模型 A/B：专门做决策的模型，值得进热路径吗

2025–2026 出现了把「决策」本身当训练目标的模型，最贴题的两个方向：

- **生成式路由 / 决策模型**：[Arch-Router-1.5B](https://huggingface.co/katanemo/Arch-Router-1.5B)
  （[arXiv 2506.16655](https://arxiv.org/abs/2506.16655)，基于 Qwen2.5-1.5B-Instruct）
  —— 输入候选 route 描述，直接输出 `{"route": ...}`，**训练目标里天生带 `other`**；
- **RL 训练的路由器**：[Router-R1](https://arxiv.org/abs/2506.09033) 与
  [LLMRouter](https://github.com/ulab-uiuc/LLMRouter) 框架 —— 把多模型路由形式化成序贯决策，
  能力更强但都要多轮推理 + 工具调用，延迟量级不适合一场 5 分钟的实时对话。

实测（`tools/qa/decision_bench.py`，24 条标注：18 条在场 + 5 条跑题 + 1 条越界）：

| 方案 | 槽位 top1 | 跑题拒绝 | 越界拒绝 | 平均耗时 | 备注 |
|---|---|---|---|---|---|
| bge-reranker（裸 argmax） | 17/18 | **0/5** | 0/1 | 114 ms | 没有「都不像」这个选项 |
| **Arch-Router-1.5B（生成式）** | 17/18 | **4/5** | 0/1 | **3374 ms（CPU）** | 拒绝语义干净，但慢 30 倍 |
| **bge + 场景门（本项目采用）** | 17/18 | **5/5** | 1/1 | 114–177 ms | 用一道独立门补上「拒绝」 |

**结论：不把决策大模型放进热路径。** 理由不是它不好，而是数据不支持：
它的核心优势（拒绝）我们用一道 16 条原型的场景门就拿到了，而且拒绝率更高（5/5 vs 4/5）、
快 20–30 倍。所以它被保留为**可选的第二意见**（`MIRA_ROUTER=auto` 时仅在 CUDA 上启用，
否则 3.4s/句会直接毁掉实时感），只用来处理「快速模型拿不准」的那一小批话。

**踩到的坑（写进代码注释了）**：路由模型会覆盖场景门——实测「今天中午吃什么」gate=-2.22
（明确跑题），路由模型却判成 `coffee`，如果让它覆盖门，兜底就形同虚设。
最终权责划分：**准入权归场景门，拒绝权归路由模型**（它说 `other` 就一定 `other`）。

## 2026-10-20 实测：这道门在生产环境里其实是**关着的**

决策层写完了、跑分也对（上表），但把 app 真正跑起来之后发现：**问"今天中午吃什么"，
她照样答了一句"中午吃的是麻辣烫，三块钱一份"还配了音。** 门一次都没生效。

三个环节单独看都"正常"，串起来是空的：

1. `_CrossEncoder.available()` 只判 `os.path.isdir(模型目录)`。这台机器上模型权重是有的、
   `mira/.venv` 里 **torch 是没装的**（`requirements.txt` 里它是可选依赖）→ `available()` 返回 True。
2. 于是 `decide()` 走 cross-encoder 分支 → `scores()` 里 `import torch` 抛 `ModuleNotFoundError`。
3. `main.run_turn` 的 `try/except` 把异常当成"决策层不可用"，`decision = None`，
   直接**放行整轮**——设计里写的关键词降级（`backend=keyword`）反而永远轮不到。

结果是：**"降级"从一个功能变成了一条静默的旁路。** 用户看到的不是"她没听懂"，
而是"她答了一句不着边际的话"，而且没有任何信号说明门没开。

修了三处，每一处都对应上面一环：

| 修法 | 位置 |
| --- | --- |
| `available()` 同时要求 `importlib.util.find_spec("torch")`，没有 torch 就走关键词门 | `app/selector.py` |
| `decide()` 里把 cross-encoder 调用包起来，异常 → 降级关键词门（**不是**放行） | `app/selector.py` |
| 把 torch + transformers 装进 `mira/.venv`（CPU 版），让真正的门跑起来 | `requirements.txt`（注释写明可选） |

顺带补了两条场景门原型：真实的第一句往往是「你好，我叫XX，你叫什么名字？」这类自我介绍，
原表里一条都没有，实测 gate=-1.24 被判成跑题——**一个刚坐下的陌生人过来打招呼，
角色直接装死，这是最难看的一种错拒**。补了「你好，你叫什么名字？」「我可以坐这儿吗？」，
复测 gate 分别升到 +8.16 / +10.31，两条跑题仍是 -2.92 / -4.29。

教训（可以对着面试讲）：
**"功能写完了"和"功能在生产里开着"是两件事。** 判据不能是"代码里有这条分支"，
必须是"跑起来之后能从事件里看到 `backend=cross_encoder` / `provider=llama` 这种字段"。
这也是为什么这一轮同时加了 `done.provider`（谁真正说了这句话）——
把"降级"从默认值变成一个必须解释的异常。
