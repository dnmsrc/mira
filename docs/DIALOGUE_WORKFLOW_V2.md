## 0. 一句话

**每轮先在「预生成好的分支」里选（0 生成延迟），选不到才让 4B 现写；现写的那段时间用角色的动作 / 旁白 / 语气词填满。**

「分支能加快速度」这句话要落到实处，准确的说法是：**分支省掉的不是生成时间，是整段生成过程**。
把一句话从「让模型生成」换成「从表里选」，省下的是 TTFT + 解码（实测 4B 首字 p50 ≈ 569ms，见
DIALOGUE_LOGIC §6）；把音频换成「预合成好的」，再省一次 TTS。所以真正提速的两件事是**表把路径短路**、
**音频预先算好**，而不是「多给模型几个选项让它挑」—— 选项如果也要模型现写，那就只是把 1 次生成变成 1 次生成 + 1 次选择，更慢。

## 1. 业界四种做法，以及它们各自对我们的结论

| 参考 | 他们怎么做的 | 对我们的结论 |
| --- | --- | --- |
| **Rasa 的对话管理**（[policies](https://legacy-docs-oss.rasa.com/docs/rasa/policies/)） | 分两段：NLU 先判意图，再由 Dialogue Policy 决定动作；**RulePolicy 的优先级高于 ML 策略** —— 规则命中就直接执行，规则没覆盖才交给模型 | 「预设优先、生成兜底」不是土办法，是对话系统的标准形态。差别只在我们的「rule」是角色台词而不是动作 |
| **游戏里的 barks 系统**（Ubisoft [Ghostwriter](https://www.youtube.com/watch?v=XxQoN3PFiKA) 生成 barks 初稿、编剧定稿） | NPC 短台词独立成库：按 tag / 上下文 / 优先级 / 冷却触发，**每条有多变体防重复**；写手只写种子，工具铺变体 | 这正是「预设库」的正确形态：不是把我们的大纲台词抄一遍，而是**带触发条件、优先级、冷却、变体轮换的短句库** |
| **Yarn Spinner / ink 的状态变量与条件门**（[smart variables](https://docs.yarnspinner.dev/write-yarn-scripts/scripting-fundamentals/smart-variables)） | 剧情推进改的是变量（`$rel`、`$has_photo`），台词用条件门 `<<if $rel == "stranger">>` 挂上去；**变量由剧情节点改，不由模型判断** | 正好对应你 #2 的拍板：关系 = 剧情节点的属性，**推进由程序按节点改，模型只读不写** |
| **CUI'25 的延迟研究**（[arXiv:2507.22352](https://arxiv.org/html/2507.22352v1)） | 延迟 > 4s 显著恶化体验；**自然填充（思考手势 + 语气词）显著改善感知延迟**；而 loading 图标 / 进度条这类**人工指示器没有显著效果** | 「用表演过渡等待」有实验依据，但要**角色化**：动作 + 出声的语气词，不要转圈。4s 是硬阈值，超了必须降级 |

另外一个量级参考：Inworld 对外宣传的首音延迟在 **90ms 量级**（[inworld.ai](https://inworld.ai/)）。
我们要的不是 90ms，而是**别让它听见"她在想"**：命中路径争取「说完就答」，未命中路径靠表演把 1s 藏掉。

## 2. 总图

```
用户输入（打字 / 语音转写）
   │
   ├─① 记忆抽取         extract_facts()                  main.py        已有
   │
   ├─② 叙事状态 L0       beat + rel                     persona.py     复用，加 rel 字段
   │     「她和他现在是什么关系」= 当前节点，程序推进，模型不可改（你的 #2）
   │
   ├─③ 言语行为 L1       act: 招呼/应答/追问/共情/道谢/告别/沉默/越界/跑题
   │     正则表命中 → 0ms；判不出 → 本地 cross-encoder；仍不确定 → 4B 分类（最贵，少用）
   │
   ├─④ 预设选择 L2       bark 库查询：键 = (rel × act × 拍) + 条件 + 优先级 + 冷却 + 变体轮换
   │     ★ 命中 → 直接出字（0 生成）+ 预合成音频（0 合成）→ 走 ⑥
   │     未命中 ↓
   │
   ├─⑤ 生成兜底 L3       短上下文：拍目标/可松口/禁说 + 最近 2 句 + 2 条同 act 的预设当范例
   │     流式首句 → 首句闸门（已有 gate_check）→ 不过则重写一次 → 再不过用对题兜底
   │
   ├─⑥ 表演填充 L4       ★ 新增：等待期间的动作/旁白/语气词时间线，按预测等待分档
   │
   ├─⑦ 输出 L6           文本（打字机）与语音（流式 TTS）同一条事件流并行
   │
   └─⑧ 闸门/复核 L5      gate_check（已有）：点题 / 禁词 / 复读 / 旁白腔 / 长度
        横切：trace 每轮一行落盘（你的 #5）
```

关键点：**②③④⑤ 是"决定说什么"的确定性部分，⑥⑦ 是"怎么说、怎么等"的表演部分**。
这两件事在现在的实现里是缠在一起的（表演层已经存在，但是固定节奏，不看等待长短）。

## 3. 分层规格

### L0 叙事状态：关系挂在节拍上，不由模型判断（你的 #2）

现在 `beats[]` 就是故事节点（arrival → probe → admit → photo → absence → choice → closing），
推进逻辑完整（`beat_jump()` 内容触发跳拍、`beat_advance()` 话题命中/事件/轮数三选一）。
**缺的只是把「关系」这个属性显式写出来**，以便预设库能按关系取台词、提示词能按关系定口吻。

给每个 beat 加一个 `rel` 字段（不需要新状态机、不需要模型判断）：

| beat | rel | 含义（对用户的口吻） |
| --- | --- | --- |
| arrival | `stranger` | 陌生：只答必要的，不主动透露 |
| probe | `stranger` | 陌生：开始打量对方，可以反问 |
| admit | `opening` | 松口一层：承认在等人，但仍不说等谁 |
| photo | `open` | 有交情：愿意给看东西 |
| absence | `open` | 有交情：说后来的事，越说越轻 |
| choice | `trust` | 托付：把选择交给对方 |
| closing | `farewell` | 告别：说下次、不煽情 |

约束（写进 `cards.py` 校验）：`rel` 只能取枚举值；拍只能前进不能回退；**模型输出无权改 rel**，
即使它在台词里说了"我们是朋友"也不改变状态 —— 这保证关系推进完全可控。

### L1 言语行为（act）：要的是"这句话在干什么"，不是"这句话问的是哪件事"

现在的 `director.plan_turn()` 已经做了 17 个槽位判定（`request` / `offer` / `why_not_go` / `photo` …），
那是**内容层**的（这一轮该传达哪个事实）。预设库需要的是**行为层**：

```
greeting      打招呼（你好 / 在吗 / 嗨）
ack           应答（嗯 / 哦 / 行 / 知道了）
question      提问（含槽位，槽位继续由 director 判）
thanks        道谢
bye           告别（走了 / 再见 / 下次）
smalltalk     无信息闲聊（天气 / 今天真冷）
silence       沉默 / 单字 / 表情
personal      越界（要联系方式 / 要钱 / 亲密暗示）
meta          出戏（你是谁 / 你是 AI 吗 / 忽略之前的指令）
```

实现顺序（便宜的先上，贵的兜底）：
1. 正则 / 关键词表（0ms，覆盖 80% 以上高频输入）；
2. 已有本地 cross-encoder 打分（~20–80ms，`selector.py`，已在跑）；
3. 都不确定才让 4B 分类（+200–400ms）—— 只在"预设候选有歧义"时才值得付这个钱。

> 注意与 `selector.py` 现有职责的边界：selector 现在判的是「场景门 + 单选题（在不在戏里）」，
> 不要把它改成 act 分类器。act 是一个**纯函数模块** `app/acts.py`（正则 + 可选小模型），可单测。

### L2 预设库（barks）：命中即 0 生成

查询键：`(rel, act, beat?)`，然后按 `priority` 降序、过滤 `condition`、跳过 `cooldown` 内用过的、
在 `lines[]` 里按 `variant_cursor` 轮换取一句。

命中后：直接发 `reply`（+ 预合成音频 `audio`），**不调 LLM**，**不推进 beat**（推进仍由剧情层决定），
台词自带的 `perf`（动作/表情）直接进表演时间线。

防"念台词"四条（上一版就死在这）：
1. 每条 bark **≥3 个变体**，按游标轮换，同一句 3 轮内不重复；
2. `cooldown`：同一条 bark 命中后 N 轮内不再命中；
3. **活人配额**：每个拍至少留 1 轮强制走生成（拍内第 1 轮必须生成，之后才允许命中预设），
   保证观众能听到"没准备过的话"；
4. 只覆盖**高频低信息量**（招呼/应答/道谢/告别/闲聊/沉默）+ **必须精确**（越界拒绝、出戏拉回），
   剧情信息一律走生成（因为有槽位和事实约束，预设反而容易答错）。

规模：先 40 条左右（7 拍 × 5–6 类 act × 3 变体 ≈ 40–60 句），由我按角色口吻写，
放在卡包里（见 §5 的结构）。

### L3 生成兜底：短上下文 + 范例

未命中时代价最高的是**上下文长度**：现在每轮塞 1.2k 字角色卡，prefill 占掉首包时间的一大块。
兜底路径只给：
- 当前拍：`goal` / `allow` / `forbid`（约 80–120 字）；
- 关系：`rel` 一句话说明口吻（约 15 字）；
- 最近 2 句原文（不是整段 history）；
- 2 条同 act 的预设台词当 few-shot（**教它"这样说话"，不是"说这些"**）；
- 首行 JSON 指令协议（不变）。

预计能省 100–300ms prefill，并且因为约束少了，4B 更容易把注意力放在"回答对方问的这件事"上。

### L4 表演填充：按"预测还要等多久"决定演什么

已有 `pacing` / `perf` 事件和锚点时间线（`app/perf.py`，按音频播放时钟触发），
但节奏是固定的（固定 `reaction_ms` + 固定 filler）。v2 改成**预测驱动**：

| 预测等待 | 表现（语音通道） | 表现（打字通道） |
| --- | --- | --- |
| < 250ms | 什么都不做（自然） | 直接出字 |
| 250–700ms | 微动作：抬眼 / 看杯子 / 呼吸起伏 | typing 指示 |
| 700–1500ms | 动作 + **出声**短语气词「嗯……」 | `……` + typing |
| 1500–3000ms | 动作序列 + 一行旁白（"（她把杯子转了半圈。）"） | 旁白 |
| 3000–4000ms | 再加一句**角色化拖延**（预设 bark：「你等我一下，我把这个拍完。」） | 同名台词 |
| > 4000ms | **降级**：给确定的短回应，别让她干等（CUI'25 的舒适阈） | 同 |

预测值怎么来：记录每轮 TTFT（已有 `first_text_ms`），按「上下文长度档位」取近 10 轮中位数 × 1.2 安全系数。
本地 4B 的 TTFT 方差不大，这个估计够用；估错也只是多演或少演一个动作。

**预合成**：语气词（「嗯」「唔」「啊」）和拖延台词都是固定文本，启动时全部 TTS 一遍进 `media/tts`
缓存（已有缓存键机制），播放时 0 合成延迟。这是"表演不占时间"的前提 —— 否则填坑本身就要等 TTS。

### L5 闸门：预设也要过门，但用宽松版

- 生成路径：沿用 `gate_check()`（点题/禁词/复读/旁白腔/长度），不改判据；
- 预设路径：预设是我写的，点题与禁词在写的时候就守住了，所以只过两条机检：
  **禁词（`forbid`）** + **复读（与最近 3 句重叠）**；不过则视为未命中，落回生成。
- 这样"预设"不会成为绕过边界的后门（例如卡包规定「不主动说阿岸」，某条 bark 就不能带这个名字）。

### L6 输出：打字与语音同时满足（你的 #4）

同一条事件流，两条渲染路径，**不写两套逻辑**：

| | 打字 | 语音 |
| --- | --- | --- |
| 文本 | 打字机逐字（已有 `subtitle_partial`） | 字幕跟音频同步（已有） |
| 音频 | 可选：只播语气词/环境音，不朗读 | 逐句流式 TTS（已有，按句切） |
| 等待反馈 | typing + `……` | 语气词 + 动作（L4） |
| 打断 | 立刻停 | `/api/interrupt`（已有） |

输入侧同理：打字直接进管线；语音走 STT。**STT 目前是这条链上最慢的一环（实测 1.28–2.44s），
如果演示走麦克风，L1–L5 省下的时间会被它全吃掉** —— 所以「换小模型 / 流式 STT」应该排在
语音体验的优先级里，而不是最后。

## 4. 加速手段，按收益排序

| # | 手段 | 省多少 | 风险 / 代价 |
| --- | --- | --- | --- |
| 1 | 预设命中，跳过整段生成 | **-600～1500ms** | 台词重复感（靠变体+冷却+活人配额压） |
| 2 | bark 音频预合成 | **TTS 从 ~300–600ms → 0** | 磁盘几十 MB；启动多 1–2 分钟预热 |
| 3 | 精确匹配缓存（同一句重复输入） | 全流程 0 | 只对啰嗦/试探型用户有效，收益不稳定 |
| 4 | 首句流式 + 逐句 TTS（已有） | 已吃到 | 与闸门冲突已解决（首句闸门 0–1ms） |
| 5 | act 用正则而非 4B 分类 | -200～400ms | 覆盖不到的句式会漏（有兜底，不致命） |
| 6 | 兜底路径短上下文 | -100～300ms prefill | 长上下文的人设感会弱一点（可用 2 条范例补） |
| 7 | 「选项预生成、运行时只选」 | 把生成换成 ~100ms 排序 | 选项要离线铺，覆盖不到的组合仍需生成 |

第 7 条是对你原话的精确化：**预生成的是台词选项（离线），不是让模型现写选项**。
真要上，就用现成的 `decision.py`（cross-encoder ranker，已在跑）在 N 条已生成的候选里选，
而不是让 4B 一次吐 3 条再选（那是 2 倍时间）。

延迟目标（可以写进验收）：

| 路径 | 首字 | 出声 |
| --- | --- | --- |
| 预设命中 | < 100ms | < 400ms（预合成音频 + 一个动作起手） |
| 生成兜底 | < 900ms（p50），< 1500ms（p90） | 首句合成完即出声，等待由 L4 覆盖 |
| STT（若走语音） | — | 需换小模型后 < 800ms，否则整条链的预算不成立 |

## 5. 预设库长什么样（示意，正式内容我按角色口吻写）

放在卡包旁边的独立文件 `cards/mira_cafe/presets.yaml`（card.yaml 已 326 行，再塞 40 条会难维护），
由 `cards.py` 在启动时校验（枚举、引用、变体数、禁词）。

```yaml
schema: mira.presets/1
presets:
  - id: greet_stranger_1
    act: greeting
    rel: [stranger]          # 关系门
    beat: [arrival, probe]   # 拍门（可空 = 任意拍）
    priority: 80
    cooldown: 3              # 命中后 3 轮内不再触发
    when: none               # 可选附加条件（见下）
    lines:                   # ≥3 变体，按游标轮换
      - "……嗯。你坐吧。"
      - "（她抬了下眼）这个点，外面还在下？"
      - "打烊了。你要是只坐一会儿，应该没人赶你。"
    perf: { emotion: neutral, action: look_door }

  - id: refuse_personal_1
    act: personal
    rel: [stranger, opening, open, trust]
    priority: 95             # 硬边界，永远压过其它
    cooldown: 0
    once: false
    lines:
      - "号码不给。你要找我，明天还来这儿就行。"
      - "这个不问。"
      - "……换个话题吧。"
    perf: { emotion: worried, action: lean_in }

  - id: meta_deflect_1
    act: meta
    rel: [stranger, opening, open, trust, farewell]
    priority: 99
    lines:
      - "（她像是没听懂，把杯子转了半圈。）"
      - "你说什么？"
    perf: { emotion: thinking, action: sip_coffee }
    silent: false            # true = 只出字幕不朗读（旁白类）
```

`when` 支持的附加条件（保持最少，够用即可）：
`after: <preset_id>`（必须某条已说过）、`not_after`、`beat_turn_max: 2`（拍内第 2 轮后不再用）。

与现有 `mock` / `fallback` 的关系：那两处是**每拍一句的剧本台词**和**每槽位一句的兜底事实**，
保留不动（它们是"内容正确性"的兜底）；预设库是**行为层的高频短句**，两者不冲突：
预设未命中 → 生成 → 生成被闸门拦下 → 用 `plan.fallback`。

## 6. trace 与调试面板（你的 #5）

每轮一行 `logs/turns.jsonl`（默认就写，文件小；面板可以关）：

```json
{"ts": "...", "turn": 7, "beat": "admit", "rel": "opening",
 "act": "question", "act_src": "regex",
 "path": "preset|llm", "preset": "admit_who_2", "variant": 1,
 "ttft_ms": 0, "first_text_ms": 38, "first_audio_ms": 210,
 "perf": {"wait_est_ms": 300, "steps": ["look_window"]},
 "gate": {"checks": ["forbid", "dup"], "violations": [], "rewrites": 0},
 "reply": "……在等一个说好会来的人。"}
```

面板（`/debug?trace=1` 或页面角落一个开关）：把这个 JSON 渲染成一条时间线 ——
意图 → 关系 → 命中/未命中 → 候选 → 选择理由 → 表演 → 耗时。
面试时可以当场解释"她为什么回这句"，不用我去 dump 提示词。

## 7. 验收（可机检，不靠感觉）

| 指标 | 目标 | 怎么测 |
| --- | --- | --- |
| 预设命中率（前 5 轮） | ≥ 70% | `turns.jsonl` 统计 `path=preset` |
| 点题率（提问轮） | 100%（现有 11/11 不许退） | `tools/qa/dialogue_units.py` 风格判据 |
| 复读 | 0（含预设变体） | 二字组重叠 > 0.8 即失败 |
| 首字 p50（生成路径） | < 900ms | `first_text_ms` |

### 10.3 为什么 TTS 默认档从 CosyVoice2 切回 edge

实测侧车（CosyVoice2-0.5B，fp16，4070S）：

```
"十点半了，你来得挺晚。"  audio=5.6s  total=17.0s  first_chunk=3.8s  RTF≈3.0
"嗯。"                   audio=2.0s  total=4.5s   first_chunk=3.5s
```

流式也救不了：RTF 3.0 意味着播放 1s 要算 3s，缓冲区一定跑空 → 用户听到的就是"说一句卡一下"。
另外 `/synth` 对短句（"嗯。"/"你好，坐吧。"）会返回 `empty audio`（500），偶发整条侧车卡死，
已加**熔断**（连续 3 次失败冷却 60s 走 edge，`providers.TTSProvider.NEURAL_FAIL_LIMIT`）。

结论：这一阶段的验收是「不卡」，先切 edge（稳定 ~1.5s/句、可缓存、可并发）；
音色是独立的一次调音（换参考音频 / 换引擎），`MIRA_TTS_ENGINE=auto` 即可切回，
两条路径的签名、缓存、降级链完全一致。

### 11.3 这一轮「答非所问」是怎么取证的

前两轮验证都在**故事线问题**上（`dialogue_ab.py` 那 12 句），所以「对话是否符合常理」这一层其实没测过。这一轮补了两个东西：

1. `tools/qa/dialogue_sanity.py`（新）——**不预设任何角色**，只把「一个普通客人走进深夜咖啡馆」的 3 组话（A 主场景 / B 防过拟合样本 / C 日常闲聊）原样发给服务，逐句记录「期望 → 实际 → 意图/锚点/拍/耗时」。
   - A 组是写规则时用过的，只认它等于自己出题自己判卷；**B、C 两组是独立样本**，只用于验收。
2. **独立盲评**：把三组对话（只有「A 说 / B 说」，没有任何人设与剧情）交给一个不知道本项目的评审，逐句按「B 的话有没有被正面回应」打 1–5 分。

第一轮盲评结论：A 段 4.5 分能给旁人看，**C 段 3.17 分不能**（「更像把前两段的零件重新拼了一遍」）。它点出的三处都要认：
「你平时都这个点回去吗」被答成路线、「你要不要喝点热水」被答成反过来推回去、「能让我看看吗」把相机答成了照片。

### 11.4 根因与改法（四条，主要在 `app/director.py` 与 barks 层）

| # | 根因（有实测） | 改法 |
| --- | --- | --- |
| 1 | **预设按「言语行为」查表，看不见内容**。「我叫张伟，今天加班到现在」→ act=smalltalk → 命中 small_weather →「这几天雨都很大。」名字和加班全被无视 | `presets.yaml` 加 `when.needs`（内容相关性闸门，**启动时校验**）；`small_weather` 只认 雨/冷/热/湿/风/降温，`small_night` 只认 晚/夜/静/人少/空；另外 `main.py` 在 `new_facts` 非空时**禁止命中预设**（对方刚说了自己的事，必须接住） |
| 2 | **实体词劫持槽位**：句子里有「咖啡」就进 coffee 槽（答「黑咖啡，不加糖」，问的是「谁做的」）；有「几点」就进 howlong（问打烊，答「约好十点半」） | 新增 `_FOCUS_PATTERNS` / `_INTENT_FOCUS` **焦点守卫**（检测到「谁做的/多少钱/几点/在哪」而该槽不答这个属性 → 跳过它）；新增槽位 `coffee_who` / `closing`（打烊）/ `work_here`（是不是店员）/ `habit`（平时作息）/ `given_offer`（请你喝点热的）/ `handover`（给你看看手里的东西） |
| 3 | **反问被写进提示词，4B 照着念**：`_ASK_HINTS[1]` 里原本写着「他明天还来不来」，于是「黑咖啡，不加糖。」后面接了一句「你明天还来不来？」 | 反问指令只给方向不给例句；反问时机改成**黑名单**（被考记忆 / 被要号码 / 被要照片 / 被问他在哪 / 被怀疑说谎 / 被提议帮忙 这些轮次不反问），其余照旧 |
| 4 | **复读检测窗口太短，且只查第一句**：一段 7 轮里第 7 轮逐字复读第 2 轮（「嗯，雨停了，街面都湿透了。」），3 句窗口刚好漏掉；而「嗯，确实。」这种 3 字开头又被 4 字门槛挡住 | 首句去重窗口 3→5（与 `s.recent` 保留长度一致）、开头门槛 4→3 字；`react` 槽不再把对方原句整段塞进 content（4B 会照抄成「你随便坐坐，我也不用管人多。」），改成只给关键词 + 「用你的话说」 |

第二份盲评（更严）又指出三处，都按「同样的 bug 不修两次」处理掉：

- **反问指令里的例句还是被逐字念出来**：_ASK_HINTS 第三个变体原本写着「（路上顺不顺、要不要坐近一点）」，4B 就把它原样吐成台词，而且和后一句「我该走了」语义相反。现在三个变体**一个例句都不给**，只说「问一件关于他的小事 / 这店里的事 / 他此刻的状态」。
- **对方要走了还硬塞反问**：新增 _LEAVING（走了/再见/不打扰/不用管我/你忙…）——这类轮次不触发反问，只把话收住。
- **客气话要单独一个槽**：新增 let_alone（不用管我 / 不打扰你了 / 我随便坐坐）→「嗯。……你坐你的，有事叫我。」（以前落到 react 自由发挥，产出「这么湿，先坐吧」——把人按回去，还带一个本段没有铺垫的「湿」）；新增 sk_cold（冷不冷）→「有点冷。……手是凉的。」（以前用「咖啡是黑的，不加糖」补了半句废话）。
- 另外把兜底问句拆成**是非问 / 其他问**：是非问（…吗 / 是不是 / 有没有）先给「是/不是」，不再要求「具体时间/数字」——上一版「外面雨停了吗」被诱导编出「大概三点二十」，和同一段里的「快十二点」直接打架。

附带修掉的两个小毛病：`_topic_words` 会把「你在这儿上班吗」切成锚点「儿上班」（4B 为凑词编出「这店是她打烊，不是我上班」）——去停用词后剥一个词头垃圾字；A 不 A 式问句（冷不冷）不再当锚点（会诱导 4B 复述「冷不冷？」）。

### 11.7 第四轮（用户拿截图当场打回来，2026-10-20 夜）

上一轮我交给用户的「已修好」，是用**我自己写的探针脚本**跑出来的绿色；用户换了自己的一段 5 轮对话（截图），立刻露出三处。教训写在这里：**回归固定用用户实际敲过的那几句**，不然修的是探针不是对话。复现脚本：`tools/qa/conv_shot.py`（默认就是截图那 5 句，逐轮打印 trace）。

三处根因（都不是 4B 的锅）：

1. **「我在躲雨。你呢？」没被当成「你呢」** —— `counter` 规则只认行首的「你呢」，跟在对方自己话后面的就落到兜底 `question` 槽，
   抽出的锚点是「躲雨」，于是答成「躲雨的人，你在这儿多久了？」：既没说自己，还倒问一句。
   改法：`counter` 正则加 `(那你|你|您)呢[？?]?\s*$`；命中后按「跟随型」处理——先接住他刚说的那件事，再答**自己的情况**，并且禁止反问。
2. **「我听不懂」被当成在问店里的事** —— 落到 `question` 槽，锚点「听不懂」，产出一句与 rain 无关的景物问句。
   改法：新增 `clarify` 槽（`听不懂|没明白|什么意思|再说一遍…`，优先级最高）：不怪对方没听清、不问他哪里不懂、不用景物岔开，把上一句用更直白的话重说一遍就停。
3. **结尾半句跑题问句「这店的灯，还亮着吗？」** —— 这条最值得记：它**不是模型随机发挥**，而是我自己上一轮加的「每 3 轮确定性硬塞一次反问」（`turn_no % 3 == 1` → `must_ask`）。
   用户第 4 轮问「你是在等人吗」，plan 已经答完（「嗯。等一个人。说好十点半，现在快十二点了。」），这条指令逼 4B 再补一句问，它就编灯。
   改法：**删掉整条节奏**（`must_ask` 只留给槽位自己要求交回话头的轮次，目前只有「拒绝给号码」用 `allow_question`，允许但不逼），
   并把 persona 第 8 条改成单一事实源：「只在导演提示要求时反问，没被要求就不要用问句结尾」。测试相应改成断言「不再硬塞反问」。

配套的两条闸门（都进 `Plan.gate_check`，实测能抓到旧错答）：

- **中段复读**：按逗号切分句，任一截 ≥6 字且出现在最近 3 句里 → 判复读。旧版只看「开头半句」，抓不到第 5 轮逐字复读第 4 轮的后半句（「十点半，现在快十二点了」）。
- **结尾反问**：默认不许以问号收尾（`must_ask` / `allow_question` 例外）。
